# 재고관리 앱 — 8-1단계 스펙: 백엔드 설정 + PIN 로그인

## 배경

로드맵 8단계(서버 + 동기화 큐)는 범위가 커서 두 개로 나누기로 했다. 이번 스펙(8-1)은 그중 "백엔드 설정 + 로그인"만 다룬다. 1~7단계(도메인 모델, 로컬 DB, 입고 등록, 재고 조회, 폐기/조정, 마감 실사, 반응형 레이아웃)는 이미 구현/테스트/커밋 완료된 상태다.

## 이번 스펙의 범위

- Supabase 프로젝트의 Auth 설정(이메일 확인 끄기, 비밀번호 최소 길이 완화) + `profiles` 테이블
- 이름 선택 + PIN 입력으로 로그인하는 화면 (온라인/오프라인 둘 다 동작)
- 사장 계정으로 로그인했을 때만 보이는 "직원 추가" 화면
- 로그인 여부에 따라 `LoginScreen`/`AppShell`을 분기하는 `main.dart` 연결

**범위 밖** (8-2 및 이후 단계에서 다룸):
- 재고 데이터(거래처/품목/로트/이동) 자체의 서버 동기화
- 거래처/품목 수정·삭제 화면에 역할(role) 기반 잠금 적용 — 그 수정·삭제 기능 자체가 아직 없음
- PIN 분실 시 "찾기" 플로우 — 사장이 직접 재설정해주는 것으로 충분하다고 보고 별도 기능을 만들지 않음
- 로그인 시도 횟수 제한/잠금 등 보안 강화 — 이번 단계에서는 다루지 않음

## 전제/결정 사항

- **8단계를 8-1(백엔드+로그인)과 8-2(동기화 큐)로 분리**했다 — 로그인/계정이 있어야 "누가 무엇을 동기화하는지"가 의미 있어지므로, 로그인부터 끝내고 넘어간다.
- **백엔드**: Supabase(Postgres) — 기존 Drift 스키마가 이미 관계형으로 설계되어 있어 그대로 옮기기 좋고, Row Level Security로 사장/직원 권한 분리가 DB 레벨에서 가능하기 때문 (이전 대화에서 이미 방향을 정함).
- **로그인 방식**: 이메일+비밀번호나 매직링크 대신 **PIN(이름 선택 + 4자리 숫자)**을 선택했다 — 매장 카운터의 공용 PC/태블릿을 여러 직원이 교대로 쓰는 실제 환경에 맞춰, 매번 이메일/비밀번호를 치는 것보다 빠르고 부담 없는 방식이다. Supabase Auth 자체는 이메일+비밀번호 방식만 지원하므로, 내부적으로는 사람마다 "가짜 이메일"(예: `직원3@내부.local`)을 만들어 그 이메일 + PIN으로 로그인하는 방식으로 감싼다.
- **세션 유지 안 함**: 앱을 껐다 켜면 매번 이름+PIN부터 다시 입력한다 — 공용 기기에서 "누가 로그인되어 있는지" 신경 안 써도 되고, 작업 기록의 귀속(누가 했는지)이 항상 확실해진다.
- **오프라인 로그인 지원**: 이 앱의 핵심 원칙(오프라인 우선)과 충돌하지 않도록, PIN 로그인은 인터넷이 없어도 동작해야 한다. 최초 온라인 로그인 성공 시 그 사람의 PIN을 해시해서 로컬 Drift DB에 캐싱해두고, 이후 오프라인 상태에서는 이 로컬 캐시와 비교해서 로그인을 허용한다. 온라인 로그인 시도가 **네트워크 오류로** 실패한 경우에만 로컬 캐시로 대체하고, 그 외의 실패(PIN 자체가 틀림)는 그대로 로그인 거부로 처리한다.
- **계정 생성**: 사장 계정은 Supabase 대시보드에서 개발자가 수동으로 1회 생성한다(이번 스펙 구현 착수 전에 진행). 이후 직원 계정은 사장이 로그인한 상태에서 앱 안의 "직원 추가" 화면에서 이름+PIN을 입력해 만든다 — 별도의 공개 회원가입 화면은 만들지 않는다.
- **PIN 해시 알고리즘**: SHA-256(솔트 포함)으로 충분하다고 본다 — 이 앱의 위협 모델은 "기기를 물리적으로 훔쳐서 로컬 DB 파일을 열어보는" 수준이라, bcrypt 같은 느린 해시까지는 과설계(YAGNI)라고 판단했다.

## 아키텍처

### Supabase 쪽 설정 (이 앱 코드가 아니라 Supabase 프로젝트 설정/대시보드에서 진행)

- Auth 설정: 이메일 확인(email confirmation) 끄기, 비밀번호 최소 길이를 4자로 낮춤
- `profiles` 테이블(Postgres): `id`(auth.users.id를 참조), `display_name`(text), `role`(text: 'owner' 또는 'staff'), `created_at`
- 사장 계정 1개를 대시보드에서 수동 생성

### 로그인 흐름

1. `LoginScreen`이 뜨면 등록된 사람들의 이름 목록을 보여준다 (로컬에 캐싱된 `profiles` 목록에서 가져옴 — 최초 실행 시에는 사장 계정 로그인을 통해 이 캐시가 채워져야 하므로, 앱을 아예 처음 설치했을 때는 최소한 한 번은 온라인 상태에서 사장이 로그인해야 한다)
2. 이름을 고르고 PIN 4자리를 입력하면, 그 사람의 가짜 이메일 + 입력한 PIN으로 `supabase.auth.signInWithPassword()`를 시도한다
3. **성공**: 세션을 메모리에 유지하고, 그 사람의 PIN을 해시해서 로컬 캐시 테이블에 저장(갱신)한 뒤 `AppShell`로 진입
4. **네트워크 오류로 실패**: 로컬 캐시 테이블에서 그 사람의 저장된 PIN 해시를 찾아 비교 — 일치하면 (오프라인 상태로) `AppShell` 진입, 불일치하거나 캐시 자체가 없으면 로그인 거부
5. **그 외 이유로 실패**(PIN이 틀림, 계정 없음 등): 로그인 거부, 에러 메시지 표시

### 직원 추가 (`AddStaffScreen`, 사장 전용)

- 로그인한 사용자의 `role`이 'owner'일 때만 접근 가능한 화면. 진입 경로는 기존 네비게이션에 "직원 추가" 항목을 하나 추가한다 — 모바일은 `MoreScreen`(7단계에서 만든 "더보기" 목록)에 항목 추가, 데스크톱은 `AppShell`의 `NavigationRail`에 6번째 목적지로 추가한다. 두 경우 다 로그인한 사용자의 role이 'staff'면 이 항목 자체를 목록/사이드바에서 숨긴다.
- 이름 + PIN 입력 → 가짜 이메일 생성 → `supabase.auth.signUp()` → 성공 시 `profiles`에 `role: 'staff'`로 저장

## 파일 구조

```
lib/
  domain/
    pin_hash.dart                    # PIN 해시 함수 (순수 함수, 테스트 가능)
  data/
    local/
      tables/
        cached_profiles_table.dart   # 오프라인 로그인용 캐시: id, displayName, role, pinHash
    repositories/
      auth_repository.dart           # 온라인 로그인 시도 → 실패 시 로컬 캐시 확인 → 성공 시 캐싱
  core/
    providers/
      auth_providers.dart            # 현재 로그인 사용자(세션) 상태 provider
  features/
    auth/
      login_screen.dart              # 이름 목록 + PIN 입력
      add_staff_screen.dart          # 사장 전용, 직원 추가
  main.dart                          # 로그인 안 됐으면 LoginScreen, 됐으면 AppShell
```

## 테스트 전략

- `pin_hash.dart`의 해시 함수 단위 테스트: 같은 PIN+솔트는 같은 해시를 내는지, 다른 PIN은 다른 해시를 내는지 — DB/네트워크 없이 테스트
- `AuthRepository`의 로직(온라인 성공 시 캐싱, 네트워크 오류 시 로컬 캐시로 대체, PIN 자체가 틀리면 거부)은 Supabase 클라이언트를 가짜(fake/mock)로 대체해서 테스트한다 — 실제 네트워크 호출 없이 세 가지 경로(성공/네트워크오류/PIN불일치)를 각각 검증
- 화면 위젯 테스트는 최소한으로: 이름 목록이 뜨는지, PIN 틀리면 에러가 뜨는지, 사장이 아니면 "직원 추가" 진입 경로가 안 보이는지
